# Jetson ARM64 交叉编译 SDK 使用说明

本文档说明**装好之后怎么用**。如何安装 SDK 请看仓库根目录的 [README.md](../README.md)。

> 本文档随 SDK 一起分发，安装完成后就在 SDK 目录下的 `使用说明.md`。
> 把 SDK 复制或打包带走时不需要再带仓库。

---

## 1. 三分钟上手

```bash
# 1. 激活 SDK（只需做一次，之后每个新终端都要做）
source ~/jetson-cross-sdk-r36.4.0/activate.sh

# 2. 用 CMake 编译你的项目
cmake -S ~/my-project -B ~/my-project/build \
      -DCMAKE_TOOLCHAIN_FILE=~/jetson-cross-sdk-r36.4.0/toolchain.cmake
cmake --build ~/my-project/build

# 3. 确认产物确实是 AArch64
file ~/my-project/build/your-app
# 预期：ELF 64-bit LSB pie executable, ARM aarch64, ...
```

> **提示**：`activate.sh` 和 `toolchain.cmake` 都写在 SDK 目录内。
> 用相对路径或 `~` 都行，脚本会自己定位。

---

## 2. SDK 目录结构

以离线脚本默认生成的 `~/jetson-cross-sdk-r36.4.0` 为例：

| 路径 | 说明 |
|---|---|
| `使用说明.md` | 本文档，随 SDK 一起分发 |
| `activate.sh` | 环境激活脚本，**用 `source` 执行，不要 `bash` 执行** |
| `toolchain.cmake` | CMake 工具链文件，通过 `-DCMAKE_TOOLCHAIN_FILE=` 传入 |
| `Linux_for_Tegra/rootfs/` | **sysroot 根目录**，即目标系统的完整文件系统 |
| `toolchain/` | Bootlin 交叉编译器（仅 x86_64 主机需要；原生 ARM64 主机使用系统编译器） |
| `downloads/` | 下载的 BSP 与 Sample RootFS 原始压缩包 |
| `escaping-symlinks.txt` | 少量目标在 sysroot 之外的符号链接清单，详见 [第 6 节](#6-关于-sysroot-里的符号链接) |
| `hello-aarch64` | 安装自检产物，可直接删除 |
| `smoke-sysroot-aarch64` | sysroot 解析自检产物，可直接删除 |
| `smoke-cuda-aarch64` | CUDA 链接自检产物，可直接删除 |
| `smoke-cudnn-aarch64` | cuDNN 编译链接自检产物，可直接删除 |
| `.setup-complete` | 存在即表示安装成功完成 |

> `downloads/` 在自检通过后会被脚本清空（约 2.5 GB 的 BSP 与 Sample RootFS 原始压缩包），rootfs 内的 apt 缓存、包索引、日志、文档、man、locale 与 Python 字节码也会一并删除。这些内容编译器无法触及，删除后可省约 7 GB。
> `escaping-symlinks.txt`、自检产物和 `downloads/` 空目录保留，方便你复核。

在线 SSH 脚本生成的 SDK 目录结构略有不同：sysroot 位于 `sysroot/`（而非 `Linux_for_Tegra/rootfs/`），并且多一个 `example/` 示例工程。

## 3. `activate.sh` 导出的环境变量

```bash
source /path/to/sdk/activate.sh
```

| 变量 | 含义 |
|---|---|
| `JETSON_SDK` | SDK 根目录，由脚本自身位置推导 |
| `JETSON_ROOTFS` | sysroot 根目录，即 `$JETSON_SDK/Linux_for_Tegra/rootfs` |
| `JETSON_CROSS` | 交叉编译器前缀，**结尾带 `-`**；原生 ARM64 主机上为空 |
| `CROSS_COMPILE` | 与 `JETSON_CROSS` 相同，供某些构建系统识别 |
| `CUDACXX` | nvcc 路径 |
| `CUDAHOSTCXX` | 编译 `.cu` 主机代码用的 g++ |
| `PKG_CONFIG_SYSROOT_DIR` | pkg-config 的 sysroot 指向 |
| `PKG_CONFIG_LIBDIR` | pkg-config 搜索路径（**注意它会覆盖宿主机的 `PKG_CONFIG_PATH`**） |

脚本里的路径全部由它自身位置推导，**不含任何硬编码绝对路径**，因此整个 SDK 目录可以随意移动、拷贝或挂载到别处（比如容器里的 `/opt/jetson-sdk`）而无需重新生成。

**唯一的例外**：x86_64 主机上的 `CUDACXX` 指向宿主机的 `/usr/local/cuda/bin/nvcc`，因为它本来就在 SDK 之外。需要换 nvcc 时可以这样覆盖：

```bash
JETSON_NVCC=/opt/cuda-12.6/bin/nvcc source /path/to/sdk/activate.sh
```

### 退出 SDK 环境

```bash
# 关闭当前终端即可；或在当前终端手动清理
unset JETSON_SDK JETSON_ROOTFS JETSON_CROSS CROSS_COMPILE CUDACXX CUDAHOSTCXX
unset PKG_CONFIG_SYSROOT_DIR PKG_CONFIG_LIBDIR
```

## 4. 三种编译方式

### 4.1 CMake（推荐）

```bash
source ~/jetson-cross-sdk-r36.4.0/activate.sh
cmake -S ~/my-project -B ~/my-project/build -G Ninja \
      -DCMAKE_TOOLCHAIN_FILE=~/jetson-cross-sdk-r36.4.0/toolchain.cmake \
      -DCMAKE_BUILD_TYPE=Release
cmake --build ~/my-project/build
```

`toolchain.cmake` 已经处理好了 sysroot、multiarch 头文件路径、库搜索路径和 CUDA 路径，通常不需要你再传 `-DCMAKE_SYSROOT`。

用 pkg-config 找依赖时，直接写即可，`PKG_CONFIG_*` 已经由 `activate.sh` 设好：

```cmake
find_package(PkgConfig REQUIRED)
pkg_check_modules(OPENCV REQUIRED IMPORTED_TARGET opencv4)
pkg_check_modules(GSTREAMER REQUIRED IMPORTED_TARGET gstreamer-1.0)
target_link_libraries(my_app PRIVATE PkgConfig::OPENCV PkgConfig::GSTREAMER)
```

### 4.2 手写 g++ 命令

不想用 CMake 时，直接用导出的变量：

```bash
source ~/jetson-cross-sdk-r36.4.0/activate.sh

${JETSON_CROSS}g++ \
  --sysroot="$JETSON_ROOTFS" \
  -isystem "$JETSON_ROOTFS/usr/include/aarch64-linux-gnu" \
  -B"$JETSON_ROOTFS/usr/lib/aarch64-linux-gnu/" \
  -L"$JETSON_ROOTFS/usr/lib/aarch64-linux-gnu" \
  -Wl,-rpath-link,"$JETSON_ROOTFS/usr/lib/aarch64-linux-gnu" \
  -Wl,-rpath-link,"$JETSON_ROOTFS/usr/lib/aarch64-linux-gnu/tegra" \
  -Wl,-rpath-link,"$JETSON_ROOTFS/usr/local/cuda/targets/aarch64-linux/lib" \
  main.cpp -o my-app
```

> **原生 ARM64 主机**上 `JETSON_CROSS` 为空，命令退化成普通 `g++`，但 `--sysroot` 依然生效。
> **x86_64 主机**上请务必保留上面这些 `-B` / `-L` / `-rpath-link` 参数，
> 否则链接器找不到 sysroot 里的 `crt*.o` 和 `.so` 开发符号链接。

### 4.3 Makefile

Makefile 不读 CMake 变量，把导出变量透传进去：

```make
CROSS   := $(JETSON_CROSS)
SYSROOT := $(JETSON_ROOTFS)

CXXFLAGS := --sysroot=$(SYSROOT) \
            -isystem $(SYSROOT)/usr/include/aarch64-linux-gnu \
            -isystem $(SYSROOT)/usr/local/cuda/targets/aarch64-linux/include \
            -I$(SYSROOT)/usr/local/cuda/targets/aarch64-linux/include
LDFLAGS  := -B$(SYSROOT)/usr/lib/aarch64-linux-gnu/ \
            -L$(SYSROOT)/usr/lib/aarch64-linux-gnu \
            -L$(SYSROOT)/usr/local/cuda/targets/aarch64-linux/lib \
            -Wl,-rpath-link,$(SYSROOT)/usr/lib/aarch64-linux-gnu \
            -Wl,-rpath-link,$(SYSROOT)/usr/local/cuda/targets/aarch64-linux/lib

my-app: main.cpp
	$(CROSS)g++ $(CXXFLAGS) $< -o $@ $(LDFLAGS)
```

## 4.4 使用 cuDNN

JetPack 开发栈由 NVIDIA 的 **`nvidia-jetpack-dev`** 元包一次装齐，它聚合了 VPI、CUDA、TensorRT、cuDNN 和 OpenCV。

仓库会同时提供多个 JetPack 版本的 bundle（r36.4 仓库里就有 6.1+b123、6.2+b77、6.2.1+b38 三套），所以脚本会按解析出的 JetPack 版本挑选对应的那套，并把整条精确版本依赖链按各自声明的版本钉住。否则一次默认安装就会拿到最新的 bundle——默认是 JetPack 6.1，却装成 6.2.1 的组件。若某个版本在仓库里没有对应 bundle，脚本会给出告警并回退到未钉版的 bundle，再不行才退回显式组件列表。

GStreamer 与 FFmpeg 的开发头文件不在该元包内，由脚本单独安装。

> 唯一的例外是 OpenCV：元包中的 `nvidia-opencv-dev` 依赖 NVIDIA 的 `libopencv-dev 4.8.0`，该版本的 `libopencv-*.so.408` 链接指向仓库从未发布的运行库，无法链接。脚本会先移除 NVIDIA 的 OpenCV 组件，再安装 Ubuntu 4.5 ABI。

cuDNN 9 最终落在 sysroot 的默认位置：
头文件 `usr/include/cudnn.h`，库 `usr/lib/aarch64-linux-gnu/libcudnn.so`。

**注意 `cudnn.h` 会 `#include "cuda_runtime_api.h"`**，所以任何用到 cuDNN 的 C/C++ 文件都必须能找到 CUDA 头文件。`toolchain.cmake` 已经处理好了，手写命令时不要漏掉 CUDA 的 `-isystem`。

CMake 工程用 `find_library` 即可，`CMAKE_LIBRARY_ARCHITECTURE` 已由工具链文件设好：

```cmake
cmake_minimum_required(VERSION 3.18)
project(cudnn_app LANGUAGES CXX)

find_library(CUDNN_LIB cudnn REQUIRED)

add_executable(cudnn_app main.cpp)
target_link_libraries(cudnn_app PRIVATE ${CUDNN_LIB})
```

> 如果 `find_library(cudnn)` 报找不到，说明 sysroot 里没有 cuDNN，见 [8.6 节](#86-cudnn-缺失)。

## 5. 编译 CUDA 代码

```bash
source ~/jetson-cross-sdk-r36.4.0/activate.sh

# .cu 文件
nvcc -ccbin ${JETSON_CROSS}g++ \
     --sysroot="$JETSON_ROOTFS" \
     -I"$JETSON_ROOTFS/usr/local/cuda/targets/aarch64-linux/include" \
     kernel.cu -o kernel

# 纯 C++ 调用 CUDA 运行时
${JETSON_CROSS}g++ --sysroot="$JETSON_ROOTFS" \
     -isystem "$JETSON_ROOTFS/usr/include/aarch64-linux-gnu" \
     -isystem "$JETSON_ROOTFS/usr/local/cuda/targets/aarch64-linux/include" \
     -L"$JETSON_ROOTFS/usr/local/cuda/targets/aarch64-linux/lib" \
     -Wl,-rpath-link,"$JETSON_ROOTFS/usr/local/cuda/targets/aarch64-linux/lib" \
     app.cpp -lcudart -o app
```

CMake 工程只要启用 `CUDA` 语言并把 `toolchain.cmake` 传进去即可，编译器路径已配好：

```cmake
cmake_minimum_required(VERSION 3.18)
project(my_cuda_app LANGUAGES CXX CUDA)
add_executable(my_cuda_app main.cu)
```

## 6. 关于 sysroot 里的符号链接

sysroot 是从 NVIDIA 官方 Sample RootFS 解出来的，其中原本有 **800 多个绝对符号链接**，例如：

```
rootfs/usr/lib/aarch64-linux-gnu/libm.so -> /lib/aarch64-linux-gnu/libm.so.6
rootfs/usr/local/cuda                    -> /etc/alternatives/cuda
```

这类链接**由操作系统按真实文件系统根 `/` 解析，而不是按 sysroot 根解析**，因此会跑到宿主机上：

- **x86_64 宿主���**上，宿主机没有对应的 AArch64 路径，链接断裂。链接器找不到 `libm.so` 时会**悄悄回退到静态库 `libm.a`**，链接方式被改变而你毫不知情。
- **ARM64 宿主机**上（原生 ARM64 流程、以及 macOS arm64 的 Docker 容器），宿主机 `/lib/aarch64-linux-gnu/` 真实存在，于是**直接链到了宿主机的 libc**，而不是 Jetson 自带的 libc。这是最危险的情况，因为它不报错。

安装脚本会自动把**目标仍在 sysroot 内部**的绝对链接改写成相对链接，使 sysroot 完全自包含。改写后例如：

```
rootfs/usr/lib/aarch64-linux-gnu/libm.so -> ../../../lib/aarch64-linux-gnu/libm.so.6
```

**少数目标本来就在 sysroot 之外的链接不会被改写**（强行改写会凭空造出不存在的路径），它们被列在 SDK 目录下的 `escaping-symlinks.txt` 里，内容形如：

```
run/shm -> /dev/shm
etc/pulse/client.conf.d/01-enable-autospawn.conf -> /run/pulse-audio-enable-autospawn
```

这些条目全部属于运行时目录、`/dev`、`/run` 或缺失的 `update-alternatives` 条目，**不参与交叉编译**，可以放心忽略。

自查命令：

```bash
# 应该只剩个位数，且都出现在 escaping-symlinks.txt 里
find ~/jetson-cross-sdk-r36.4.0/Linux_for_Tegra/rootfs -type l -lname '/*' | wc -l
```

## 7. 部署到 Jetson 上验证

交叉编译的产物**必须在 Jetson 真机上运行**（x86_64 主机上无法直接执行 AArch64 程序）。

```bash
scp ~/my-project/build/my-app user@jetson:/tmp/
ssh user@jetson 'chmod +x /tmp/my-app && /tmp/my-app'
```

部署前可先用 `readelf` 确认动态库依赖都是目标平台上真实存在的：

```bash
source ~/jetson-cross-sdk-r36.4.0/activate.sh
${JETSON_CROSS}readelf -d ~/my-project/build/my-app | grep NEEDED
```

## 8. 常见问题排查

### 8.1 `bits/xxx.h: 没有那个文件或目录`

Debian multiarch 把 libc 头文件放在 `usr/include/aarch64-linux-gnu/`，而 `--sysroot` 只会加 `usr/include`。

用 CMake 时 `toolchain.cmake` 已自动处理；手写命令时必须自己加：

```bash
-isystem "$JETSON_ROOTFS/usr/include/aarch64-linux-gnu"
```

### 8.2 `cannot find -lm` / `cannot find Scrt1.o`

链接器没在 sysroot 里找到库或启动对象。缺以下参数之一：

```bash
-B"$JETSON_ROOTFS/usr/lib/aarch64-linux-gnu/" \
-L"$JETSON_ROOTFS/usr/lib/aarch64-linux-gnu" \
-Wl,-rpath-link,"$JETSON_ROOTFS/usr/lib/aarch64-linux-gnu"
```

### 8.3 `cannot find -lcudart`

CUDA 运行库在 sysroot 的专用目录里，需要显式指定：

```bash
-L"$JETSON_ROOTFS/usr/local/cuda/targets/aarch64-linux/lib" \
-Wl,-rpath-link,"$JETSON_ROOTFS/usr/local/cuda/targets/aarch64-linux/lib"
```

### 8.4 `crt/host_config.h: 没有那个文件或目录`

sysroot 里的 CUDA 开发头文件不完整——`cuda_runtime.h` 需要 `include/crt/` 下的编译器内部头文件，但它们由**独立软件包 `cuda-crt-<版本>`** 提供，`cuda-cudart-dev` 只装了 `include/` 下的薄包装头。

```bash
# 确认是否缺失
ls ~/jetson-cross-sdk-r36.4.0/Linux_for_Tegra/rootfs/usr/local/cuda/targets/aarch64-linux/include/crt/host_config.h
```

安装脚本已经会尝试安装 `cuda-crt-<版本>`；若该软件包在你的仓库中不可用，安装时会打印告警。**在 x86_64 主机上通常不影响**：CUDA 头文件由宿主机 nvcc 提供，只有在**原生 ARM64 主机**上才会真正缺头文件。此时可在 rootfs 内补装该包后重跑安装脚本。

### 8.5 `pkg-config` 找不到包

`activate.sh` 把 `PKG_CONFIG_LIBDIR` 指向了 sysroot，并且 **取消掉了 `PKG_CONFIG_PATH`**（避免误用宿主机版本）。确认变量正确：

```bash
source ~/jetson-cross-sdk-r36.4.0/activate.sh
echo "$PKG_CONFIG_LIBDIR"
pkg-config --modversion opencv4
```

### 8.6 cuDNN 缺失

`find_library(cudnn)` 找不到，或 `#include <cudnn.h>` 报文件不存在：

```bash
ls ~/jetson-cross-sdk-r36.4.0/Linux_for_Tegra/rootfs/usr/include/cudnn.h
ls ~/jetson-cross-sdk-r36.4.0/Linux_for_Tegra/rootfs/usr/lib/aarch64-linux-gnu/libcudnn.so
```

安装脚本会安装 `libcudnn9-cuda-12` 与 `libcudnn9-dev-cuda-12`，并在缺失时直接报错退出，所以正常流程不会遇到这种情况。若是历史 SDK 目录，补装后**必须重跑一次安装脚本**——因为新装的包会重新引入 `/etc/alternatives/...` 形式的绝对符号链接，只有脚本里的归一化步骤能修掉（见第 6 节）。

### 8.7 `cudnn.h: cuda_runtime_api.h: 没有那个文件或目录`

sysroot 的 CUDA 头文件不完整。`cuda_runtime_api.h` 自身也 `#include "crt/host_defines.h"`，该文件由 `cuda-crt-<版本>` 提供。见 [8.4 节](#84-crthost_configh-没有那个文件或目录)。

`toolchain.cmake` 会自动回退到 `$CUDACXX` 旁边的完整头文件（x86_64 主机上来自 `cuda-crt-cross-aarch64`），所以一般无需手动处理。

### 8.8 换了 CUDA 版本后要重新初始化

sysroot 与 CUDA 版本是绑定的。切换 JetPack / L4T / CUDA 版本请重新运行安装脚本，**不要**在旧 SDK 上改环境变量。

## 9. 迁移与备份

整个 SDK 目录是自包含的，**可以直接打包带走**：

```bash
tar --zstd -cf jetson-cross-sdk-r36.4.0.tar.zst -C ~ jetson-cross-sdk-r36.4.0
```

在新机器上解开后直接 `source activate.sh` 即可，无需重新生成任何文件——因为脚本内部不含绝对路径。

> 体积参考：JetPack 6.1 的 SDK 清理后约 17 GB。用 zstd 压缩后约 5.8 GB，用 gzip 约 7.8 GB，zstd 明显更小且速度相当。
> 其中 rootfs 约 13 GB 是必需的 AArch64 库与头文件。
> macOS 上可以直接用封装好的命令：
> `./setup-jetson-cross-sdk-macos-arm64.sh archive 6.1`
>
> 解压需要支持 zstd 的 tar（GNU tar 1.31+、macOS 自带 tar 均支持）。若目标机器的 tar 较旧，先 `zstd -d` 再 `tar -xf`。
